# Cluster page: replace k9s with an Argo-only view

- Status: Built on 2026-11-19, tested against a fake Argo only. See "As built" at the end.
- Date: 2026-11-19

## Summary

Add a `/cluster` page to the PR Dashboard (since renamed Foreman) that covers what k9s is used for day to day: pod status, live logs, and the occasional restart. It also shows the commit each pod runs, linked to its PR, and lets you refresh and sync Argo CD apps. The page reaches both environments only through the Argo CD API. It never touches kubeconfig or `cs-cli`.

- **Prod** is the default tab. **Staging** is a second tab.
- Each deploy run in the side panel links to the apps it shipped and shows whether they run its commit yet.
- A write on prod (restart or sync) first shows a confirm dialog with the diff.

## Mocks

Static mocks of every screen are in [cluster-page-mocks/](cluster-page-mocks/README.md), and live on the [Cluster Page Mocks canvas](https://claude.ai/artifact/ThVXu5TWot1AMHgDw8zqVk). They cover:

- the Prod app list
- app detail
- logs
- the Staging tab and error states
- the two prod confirm dialogs
- deploy-run links

The mocks settle two layout choices that the design below follows:

- The app list puts apps with problems first by default: degraded, progressing, or out of sync. Healthy apps beyond the first few collapse behind "Show N more healthy apps".
- The prod restart confirm lists the pods that will be replaced and needs one click. The server still checks the app name it receives (Write safety).

## Goal and boundaries

**In scope**

- Read: for each app, its sync status, health, and git revision. For each pod, its phase, ready count, restarts, age, and image SHA, with the SHA linked to its PR.
- Logs: a live tail of one pod or every pod in a deployment. A toggle switches to the previous container. Include and exclude filter rules, a pause button, and a choice of container.
- Write: restart a Deployment, and refresh then sync an app.
- Links from deploy runs and PR cards to the apps they shipped.
- Both environments, with a separate token for each.

**Out of scope**

- Direct Kubernetes access: kubeconfig, `cs-cli`, exec, port-forward, scale, deleting pods, and editing manifests.
- Rollback. Rolling back is a git revert in `infrastructure`.
- Any resource that no Argo app manages.
- Kubernetes events. This is a likely follow-up, through `GET …/events`.
- Linear tickets and the `to-spec` and `to-tickets` tooling. This spec stays informal.
- Fixing the shared Argo admin credential. That's a separate task, listed in Follow-ups.

## Prerequisites (manual, before any write works)

These live outside this repo. Read-only work can start before P1 lands by using a token with `role:readonly`.

**P1. A `pr-dashboard` Argo account in both clusters.** Make the change in `infrastructure/apps/argo/values_prd.yaml` and `values_stg.yaml`:

```yaml
configs:
  cm:
    accounts.pr-dashboard: apiKey        # no login: token only
  rbac:
    policy.csv: |
      # …existing lines…
      p, role:pr-dashboard, applications, get,  default/*, allow
      p, role:pr-dashboard, applications, sync, default/*, allow
      p, role:pr-dashboard, applications, action/apps/Deployment/restart, default/*, allow
      p, role:pr-dashboard, logs, get, default/*, allow
      g, pr-dashboard, role:pr-dashboard
```

Then generate a token in each environment:

```bash
argocd account generate-token --account pr-dashboard
```

The role covers every app in project `default`, which includes `argocd`, `loki` and the others, not only the `svc` apps. The UI shows only `svc` and `job` apps (see "Which apps are shown"). Limiting the role to those apps would need a separate Argo project, which is listed in Follow-ups.

**P2. Cloudflare Access service token.** Create a service token, and add a Service Auth policy for it to the Access application in front of each Argo host. If the two hosts are separate Access applications, the token must be allowed on both. You may also choose to issue one token per host.

**P3. Secrets in Doppler.** The secrets live in the Doppler project `foreman` (first named `matt-pr-dashboard`), config `prd`. They are injected into the server's environment at launch, so no secret is written to a file on disk:

```bash
doppler run --project foreman --config prd -- npm start
```

The variables are:

```bash
ARGO_PRD_URL=https://argo.internal.cloudspot.io
ARGO_PRD_TOKEN=...
ARGO_STG_URL=https://argo.internal.beta-cloudspot.io
ARGO_STG_TOKEN=...
CF_ACCESS_CLIENT_ID=...
CF_ACCESS_CLIENT_SECRET=...
# optional per-env overrides: CF_ACCESS_PRD_CLIENT_ID, CF_ACCESS_STG_CLIENT_SECRET, …
```

Status: the prod values are set. The staging values are not filled in yet, because staging access isn't available for now. The `prd` config holds both clusters' variables; Doppler's `stg` config is unused.

If an environment's URL or token is missing or empty, its tab says "not configured" and names the missing variable. The rest of the dashboard keeps working. An empty string counts as missing, so a blank `ARGO_STG_TOKEN` gives the "not configured" state, not a failed request.

As a fallback for running without Doppler, the server also reads `~/Library/Application Support/merge-watch/argo.env` (mode `0600`, same variables). Variables in the process environment override the file, following the pattern in `server/config.ts`. The server never logs these values or sends them to the browser.

**Keeping secrets away from agents.** A logged-in Doppler CLI hands out secrets without a prompt, so any agent running as you could read them. Two things reduce that risk:

- Add deny rules to `~/.claude/settings.json` for `Bash(doppler secrets:*)`, `Bash(doppler run:*)` and `Read(~/Library/Application Support/merge-watch/argo.env)`, and turn on the Claude Code sandbox so the read rule is enforced for shell commands too.
- Generate Argo tokens with an expiry, for example `--expires-in 30d`, and rotate them.

An agent can also call the local write endpoints without knowing any token. The guard against that is in "Write safety".

## Design

### Architecture

```
browser ──/api/cluster/*──▶ dashboard server (127.0.0.1) ──HTTPS──▶ Cloudflare Access ──▶ Argo CD API
                                   │                                  (prd / stg)
                                   └── GitHub API (existing token): SHA → PR, mono-build.env
```

- `server/argo.ts` holds one `ArgoClient` for each environment. Each client sends `Authorization: Bearer <token>`, `CF-Access-Client-Id` and `CF-Access-Client-Secret` on every request. Secrets stay in memory. They're never logged, and never sent to the browser.
- `server/cluster.ts` holds a `ClusterWatcher` for each environment. It opens Argo's watch streams only while at least one browser is subscribed to that environment. It closes them 30 seconds after the last browser leaves.
- `core/cluster.ts` holds pure logic: parsing image refs, choosing which apps to show, the log filter, matching runs to apps, and the prod write guard. Its tests go in `core/cluster.test.ts`.
- `web/src/ClusterPage.tsx` with `ClusterTabs`, `AppList`, `AppDetail` and `LogsPanel`.
- The router (`web/src/router.tsx`) gets a `cluster` route at `/cluster?env=prd|stg&app=<name>`. `TopBar` gets a Cluster link.

### Argo API calls used

All requests go to the environment's base URL. Verify each path against `GET /api/version` before building on it (see Open questions).

| Purpose | Argo call |
|---|---|
| App list and live updates | `GET /api/v1/stream/applications?projects=default` (SSE), seeded by `GET /api/v1/applications?projects=default` |
| Pods of one app, live | `GET /api/v1/stream/applications/{app}/resource-tree` (SSE), seeded by `GET /api/v1/applications/{app}/resource-tree` |
| Logs | `GET /api/v1/applications/{app}/logs?namespace=default&podName=…&container=…&follow=true&tailLines=500&previous=…&sinceSeconds=…`. For a whole deployment, use `kind=Deployment&group=apps&resourceName=cloudspot-{app}` instead of `podName`. |
| Refresh | `GET /api/v1/applications/{app}?refresh=normal` |
| Diff | `GET /api/v1/applications/{app}/managed-resources`. Compare `liveState` to `targetState` for each resource that is out of sync. |
| Sync | `POST /api/v1/applications/{app}/sync` with body `{ "revision": "<target revision from the preview>", "prune": true }` |
| Restart | `POST /api/v1/applications/{app}/resource/actions` with `namespace=default&resourceName=cloudspot-{app}&kind=Deployment&group=apps&version=v1` and body `"restart"`. Argo v3 may use `…/resource/actions/v2` with `{ "action": "restart" }`, so pick the one `/api/version` supports. |

### Which apps are shown

An app is shown when its `metadata.ownerReferences` names the ApplicationSet `svc` or `job`. The list groups apps under "Services" (`svc`) and "Jobs" (`job`). Every other app in the project is hidden, which covers `argocd`, `loki`, `traefik` and the rest. `core/cluster.ts` exports `isShownApp(app)`.

### Commit and PR on each pod

- `parseImage("registry.digitalocean.com/cloudspot/api-server:f8f6…febe")` returns `{ service: "api-server", sha: "f8f6…febe" }`. Any tag that isn't 40 lowercase hex characters returns `sha: null` and is shown as is.
- The server resolves each SHA with `GET /repos/CloudSpot/cloudspot/commits/{sha}/pulls`, using the existing `GitHub` client and its ETag cache. It keeps the first merged PR.
  - Results go in an in-memory `Map<sha, PrRef | null>`. A commit's PRs don't change, so the map is never invalidated.
  - It resolves at most 4 SHAs at a time.
- The UI shows `f8f6d60` · `#1234 PR title`, linking to the PR. A SHA with no PR shows the short SHA, linking to the commit. A pod whose SHA differs from the app's other pods is marked "mixed", for example in the middle of a rollout.

### Linking deploy runs to apps

- `GhRun` gains `headSha`, taken from the REST field `head_sha`. Bump `SNAPSHOT_SCHEMA` to 8.
- For each finished "Build `<service>`" job, the server reads `services/<service>/mono-build.env` at the run's `headSha`, using `GET /repos/CloudSpot/cloudspot/contents/...?ref=<headSha>`, and parses `K8S_TARGETS`. Results are cached by `(service, sha)`. `svc/x` maps to Argo app `x` and `job/x` to app `x`.
- For each target app, in staging always and in prod when the PR has `deploy-prod`, the run row and the PR card show:
  - **live:** every pod of the app runs `headSha`.
  - **rolling:** some pods do.
  - **waiting:** no pod does yet, and the app's `status.sync.revision` hasn't moved. Argo hasn't picked up the infrastructure commit.
  - **replaced:** pods run a newer SHA from a later merge.
- Each status links to `/cluster?env=…&app=…`.
- These statuses are computed only while the Cluster watcher for that environment is open, or from a one-shot `GET /api/v1/applications/{app}` when a run row is expanded. The 30-second runs poll never calls Argo.

### Local server API

The browser talks only to these routes. All of them are under the existing loopback `Host` check.

| Route | Returns |
|---|---|
| `GET /api/cluster/config` | `{ envs: [{ id: "prd" \| "stg", label, configured: boolean, missing: string[] }] }` |
| `GET /api/cluster/:env/events` (SSE) | An `apps` event carrying a `ClusterApp[]` snapshot. Sent on connect and on every change, debounced to 1 per second. |
| `GET /api/cluster/:env/apps/:app/tree` (SSE) | A `tree` event carrying `{ pods: ClusterPod[], deployment: { name, desired, ready, updated } }` |
| `GET /api/cluster/:env/apps/:app/logs?pod=&container=&previous=0\|1&tail=500` (SSE) | A `line` event with `{ pod, container, ts, text }`. An `end` event when Argo closes the stream, and an `error` event with `{ status, message }`. |
| `POST /api/cluster/:env/apps/:app/preview` | Runs a refresh, then a diff. Returns `{ previewId, revision, resources: DiffEntry[], expiresAt }`. |
| `POST /api/cluster/:env/apps/:app/sync` | Body `{ previewId }`. Returns 409 if the app's target revision changed since the preview, or if the preview is older than 2 minutes. |
| `POST /api/cluster/:env/apps/:app/restart` | Body `{ confirm: "<app>" }` on prod, `{}` on staging. |

```ts
// core/types.ts additions
export type ClusterEnv = "prd" | "stg";
export interface PrRef { number: number; title: string; htmlUrl: string }
export interface ClusterApp {
  name: string;
  group: "svc" | "job";
  sync: "Synced" | "OutOfSync" | "Unknown";
  health: "Healthy" | "Progressing" | "Degraded" | "Suspended" | "Missing" | "Unknown";
  revision: string | null;          // infrastructure commit Argo synced
  operation: { phase: string; startedAt: string } | null;
  image: { service: string; sha: string | null; pr: PrRef | null; mixed: boolean } | null;
  pods: { ready: number; total: number; restarts: number };
}
export interface ClusterPod {
  name: string;
  phase: string;                    // from the resource-tree node's health and info
  ready: string;                    // "1/1"
  restarts: number;
  createdAt: string;
  containers: string[];
  image: { sha: string | null; pr: PrRef | null };
}
export interface DiffEntry { kind: string; name: string; status: "OutOfSync" | "Missing" | "Extra"; patch: string }
```

### Write safety

- **CSRF guard.** Every `POST /api/cluster/*` requires an `Origin` header equal to the dashboard's origin (`http://localhost:<port>` or `http://127.0.0.1:<port>`), and `content-type: application/json`. Anything else gets 403. The current `Host` check stops DNS rebinding, but not a cross-site form post from another page in the same browser.
- **Prod sync.** The button reads "Refresh & sync". It calls `preview`, which refreshes the app and fetches the diff. The dialog shows:
  - the target revision
  - each out-of-sync resource with its patch
  - for a changed `imageTag`, the old and new SHA with the PR each one came from

  One Confirm click sends `{ previewId }`. The server syncs exactly the revision it previewed.
- **Staging sync.** The same flow, without the dialog. A toast shows the result.
- **Restart.**
  - Prod: the dialog shows the deployment name, its replica count, and the pods that will be replaced. Confirm sends `{ confirm: "<app>" }`, and the server checks that the name matches.
  - Staging: one click.
- **Style.** The Staging tab and every staging dialog use a distinct accent color, and the words "STAGING" in the header. Prod dialogs say "PRODUCTION" in red.
- **Local callers.** The Origin check stops web pages, not local processes. An agent could `curl` the preview endpoint and then the sync endpoint without ever seeing a token. So for prod writes the server shows its own macOS dialog (`osascript` `display dialog`, default button Cancel, gives up after 60 seconds) before it calls Argo. Approval happens outside the browser and outside any agent. `ARGO_NATIVE_CONFIRM=0` turns it off.
- **Audit log.** The server writes one line per write to `<dataDir>/cluster-actions.log`: time, environment, app, action, Argo response status. Tokens are never written.

### Log filter

- Rules are a list of `{ mode: "include" | "exclude", text: string, regex: boolean }`.
- A line is shown when no include rule exists or at least one include rule matches, and no exclude rule matches.
- Matching ignores case. A regex rule with an invalid pattern is shown in red and ignored.
- Filtering runs in the browser on a ring buffer of the last 5,000 lines per panel, so changing the rules re-filters lines already received.
- Pause stops rendering, not receiving. A counter shows how many lines arrived while paused.
- The "previous container" toggle reopens the stream with `previous=true&follow=false`. It's offered only for a pod with at least one restart.
- Rules persist per app in `localStorage`, since this is a convenience for one viewer.

### Errors

| Condition | What the user sees |
|---|---|
| A 302 or 403 from Cloudflare (`cf-mitigated` header or a redirect to `cloudflareaccess.com`) | "Cloudflare Access rejected the service token for `<host>`" |
| 401 from Argo | "Argo token for `<env>` is invalid or expired" |
| 403 from Argo | "Argo account lacks permission: `<action>`". The message names the `policy.csv` line from P1. |
| Network error or a dropped stream | The tab shows "reconnecting". Retries back off from 1 to 30 seconds, and the last snapshot stays on screen. |
| Logs for a pod that is gone | An `end` event, and the panel says "pod no longer exists". |

## Rollback

It's a local tool. Revert the commit, or delete `argo.env` to turn the page off. Removing the `pr-dashboard` account from `policy.csv` revokes its access in both clusters.

## Open questions

1. **Argo v3 API shapes.** Is the restart path `/resource/actions` or `/resource/actions/v2` on our version? Does the resource tree's pod node still carry `Restart Count` in `info`? Check `GET /api/version` and one resource-tree response from staging before step 3.
2. **Logs RBAC.** In v3, `logs, get` is enforced by default. Confirm that `role:pr-dashboard` needs it explicitly, and that a deployment-level log stream works with only that permission.
3. **Cloudflare Access.** Is there one Access application for each host, or one covering `*.internal.*`? That decides whether one service token is enough.
4. **Manual sync with auto-sync on.** With `automated` sync, a manual sync mostly only helps when the refresh shows a pending `imageTag`. Should the button be disabled, with a "nothing to sync" note, when the preview diff is empty?
5. **SHA to PR for squash merges.** `commits/{sha}/pulls` returns the PR for a squash-merge commit on `main`. Confirm it does for our merge method, including merges made by the claude[bot].

## As built

What differs from the design above, and what is still unchecked.

- **Multi-source apps.** `svc` and `job` apps have two sources (the Helm chart and the infrastructure repo), so Argo reports `status.sync.revisions`, not `status.sync.revision`. The preview stores the whole list, and the sync sends `{ revisions, sourcePositions, prune: true }`.
- **Log events.** A failed log stream sends `fail`, not `error`, because `EventSource` uses `error` for its own connection errors. Lines arrive in batches (`lines` event, an array).
- **Extra read routes.** `GET /api/cluster/:env/apps/:app/pods/:pod` returns a pod's container names for the logs picker, and `GET …/restart-plan` returns the pods a prod restart would replace. Deploy-run links use `GET /api/cluster/runs/:id/targets`.
- **No snapshot change.** `GhRun` gained `headSha`, but deploy-run statuses come from their own route, so `SNAPSHOT_SCHEMA` stayed at 8.
- **Replaced or waiting.** `deployState` asks GitHub's compare API whether a pod's SHA is newer than the run's (cached per pair).
- **Pod counts in the list.** The Application object has no pod counts, so the watcher reads each shown app's resource tree when the app changes and every 30 seconds, 4 at a time.
- **Restart route.** The client tries `POST …/resource/actions` with body `"restart"`, then the v2 route if the server answers 404, 405 or 501.
- **Services and Jobs tabs.** The list has a Services tab (the default) and a Jobs tab (`?tab=jobs`), each with a count of apps that need attention. This replaces the grouped list and the "Show N more healthy apps" collapse.
- **Hidden apps.** Any app can be hidden from the list. The names live in `<dataDir>/cluster-hidden.json` (`{ "hidden": [...] }`), one list for both environments, through `GET` and `POST /api/cluster/hidden`. Hidden apps sit in a collapsed "N hidden" section with Unhide buttons, which also says how many of them need attention. If storage needs grow, SQLite is the next step.
- **Fake Argo.** `server/fakeArgo.ts` (`pnpm fake-argo`) serves the endpoints above with sample apps. `server/cluster.test.ts` runs against it.

Not yet checked against the real clusters:

- the stream message format and the pod `info` fields (open question 1)
- the restart route on our Argo version, and whether logs need `logs, get` (open questions 1 and 2)
- deploy-run links with a real run. None of the PRs merged in the last 24 hours built a service, so the panel had nothing to show.
